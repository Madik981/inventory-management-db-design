# Консольный клиент для защиты

## Самый короткий путь

1. Открой **Docker Desktop**. В терминале проекта выполни `docker compose up -d --wait`.
2. Запусти `start_console.cmd` двойным щелчком или командой `./start_console.cmd`.
3. В меню нажми **1** — подготовить отдельную базу. Повторное нажатие сохраняет данные.
4. Нажми **S**, если хочешь показывать преподавателю SQL вместе с результатами.
5. Нажми **D** → выбери сценарий или **9** для всей защиты.

Между шагами нажимай **Enter**. Так можно сначала объяснить действие, потом выполнить его.
Гонка двух сессий выполняется автоматически без пауз внутри открытой транзакции.
**Ctrl+C** возвращает в меню. **Q** завершает клиент. Если прервана запись, её исход
нужно проверить: пункт **9** повторяет последний запрос с прежним ID.

Если `.venv` ещё не создана, сначала выполни `./ops/prepare.ps1`.
Клиент использует уже имеющийся `psycopg2`; новых библиотек устанавливать не нужно.
Альтернативный запуск:

```powershell
./.venv/Scripts/python.exe -X utf8 inventory_console.py
```

## Что находится в меню

| Пункт | Назначение |
| --- | --- |
| 1 | Создать `inventory_console`, загрузить SQL проекта и начальные остатки |
| 2 | Остатки; фильтр по товару; актуальное чтение, primary или advisory replica |
| 3 | Зарезервировать одну или несколько пар склад–товар одним заказом |
| 4 | Выбрать заказ по номеру строки; подтвердить, отменить или проверить истечение |
| 5 | Приёмка / списание с причиной и ID операции |
| 6 | Создать перемещение, отправить, принять, отменить или отметить потерю |
| 7 | События; один проход expiry-worker; доставка пакета Outbox |
| 8 | Primary/standby, синхронная репликация, WAL-позиции и инварианты |
| 9 | Повторить последнюю запись с теми же ID и параметрами |
| D | Восемь проверяемых сценариев защиты |
| S | Включить / выключить показ SQL и параметров |
| Q | Выход |

Значения в `[скобках]` выбираются нажатием Enter. Например, резерв одного iPhone
в Алматы: **3**, затем Enter для количества позиций, склада, товара, количества и ID.
Для подтверждения: **4** → номер строки нужного заказа → **1**.
Полный UUID можно вставить вместо номера строки. Списки ограничены по размеру;
известные ID можно вводить вручную.

Статусы: `active` — резерв; `confirmed` — покупка; `released` — отменён;
`expired` — истёк. Для перемещения: `requested` → `in_transit` → `received`.
`available = on_hand − reserved`.

## Сценарии для показа

Каждый сценарий получает новый учебный товар. Его можно повторить без сброса базы.
Записи сохраняются, чтобы после демонстрации посмотреть их через меню. Начальные
товары 17 и 99 остаются для ручных операций. `PASS` выводится после проверок
фактических данных, а не просто после отправки SQL.

| № | Сценарий | Что объяснять |
| --- | --- | --- |
| 1 | Покупка с двух складов, повтор, подтверждение, отмена | Атомарный резерв, идемпотентность, `on_hand` и `reserved` |
| 2 | Недостаток на втором складе + явный ROLLBACK | Нельзя оставить частичный заказ или событие откатившейся операции |
| 3 | Истёкший резерв и позднее подтверждение | Срок проверяется в БД, даже если worker ещё не успел |
| 4 | Два покупателя, один товар | Две реальные сессии; блокировка B, MVCC-чтение, COMMIT A, отказ B |
| 5 | Приёмка и чтение после записи | WAL-токен, синхронный ACK, replay, источник чтения и fallback |
| 6 | Партиции и EXPLAIN | 16 HASH-партиций по складу; partition pruning; одна БД |
| 7 | Отправка и приёмка между складами | Товар в пути, отдельные короткие транзакции, повтор без двойного списания |
| 8 | Outbox/Inbox и потерянный ACK | Сбой после COMMIT потребителя, повторная доставка, дедупликация |

Для короткой защиты: **1 → 4 → 2 → 5 → 8**. Остальные доступны для вопросов.
Вся последовательность: **D → 9**. SQL в сценариях вызывается из тех же файлов,
функций и Python-клиента, что и основной проект.

В сценариях 3 и 8 время конкретного учебного резерва/lease переносится в прошлое
административным запросом. Это явно подписанная учебная фикстура, которая заменяет
ожидание 15 минут / 30 секунд. Само завершение резерва и доставка используют
настоящие функции проекта. Сценарий 5 не останавливает реплику и не создаёт
искусственную задержку: `source` и `reason` показывают фактическое поведение.

## Где выполняются операции

По умолчанию клиент работает с **inventory_console** на том же primary и standby.
Он не сбрасывает `inventory_case2` или прежнюю `inventory_defense`.
Первичная подготовка требует административного пользователя; настройки лаборатории
уже подходят. При повторной подготовке существующая схема не изменяется.

В `inventory_console` **нет постоянно работающих фоновых воркеров**. Их один проход
можно вызвать пунктом 7. Позднее подтверждение всё равно проверяет срок резерва.
Обычные Docker workers продолжают обслуживать `inventory_case2`.
Outbox использует настоящую отдельную projection-базу; события консоли отделены
полем `source = inventory_console`. Projection показывает изменения, а не полный
остаток с учётом начального запаса.

Для работы с основной базой:

```powershell
./start_console.cmd --database inventory_case2
```

Здесь обычные операции меню изменяют основные данные. Подготовка и учебные сценарии
для этой базы запрещены. Имя базы и адрес сервера всегда видны в заголовке меню.
Адреса и учётные данные берутся из тех же переменных окружения, что у `inventory_client.py`;
`--database` выбирает базу явно (по умолчанию всегда `inventory_console`, независимо от `PGDATABASE`).
Для projection используются `SINK_PGHOST`, `SINK_PGPORT`, `SINK_PGUSER`,
`SINK_PGPASSWORD`, `SINK_PGDATABASE` из `workers.py`.

Последний запрос записывается **до отправки** в `.state/console/`. Файл содержит
ID и параметры, без паролей. Пункт 9 работает после перезапуска и сохраняет
идемпотентность при потере ответа. История отделена по адресу, базе и пользователю.
Хранится только последний запрос: при спорном результате повтори его до новой записи.
Сценарии тоже используют этот механизм; некоторые намеренно отклонённые запросы
при повторе снова будут отклонены. Read token текущего сеанса выводится при включённом SQL.

## Команды без меню

```powershell
# Подготовить базу и показать состояние
./.venv/Scripts/python.exe -X utf8 inventory_console.py --setup --status

# Гонка за последний товар, с показом SQL
./.venv/Scripts/python.exe -X utf8 inventory_console.py --demo race --show-sql

# Все сценарии без остановок между шагами
./.venv/Scripts/python.exe -X utf8 inventory_console.py --demo all --no-pause

# Проверить сам клиент: ввод, сохранение ID, ручное меню и реальные сценарии
./.venv/Scripts/python.exe -X utf8 tests/verify_console.py --integration
```

Имена сценариев: `checkout`, `rollback`, `expiry`, `race`, `replication`,
`partitioning`, `transfers`, `outbox`, `all`.
Параметр `--no-pause` удобен для репетиции и автоматической проверки.
Ошибка даёт ненулевой exit code. Интеграционные тесты создают свою временную базу
и удаляют только свои данные после выполнения.

Если PostgreSQL недоступен, клиент показывает ошибку и команду запуска Docker,
а интерактивное меню остаётся открытым. Если synchronous standby недоступен,
COMMIT может ждать подтверждения; клиент сохраняет политику синхронной записи
проекта. Таймаут или прерывание сами по себе не доказывают, что запись откатилась.

Реализация: `inventory_console.py` — меню и ввод; `defense_scenarios.py` — сценарии;
`inventory_client.py` — существующие операции и маршрутизация чтений;
`workers.py` — существующая обработка истечения и доставка событий.
